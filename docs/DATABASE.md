# DATABASE

Mazi's data lives in **Convex**. The schema is code: [`convex/schema.ts`](../convex/schema.ts) (app tables) and [`convex/betterAuth/schema.ts`](../convex/betterAuth/schema.ts) (auth tables, generated). Access rules are in [`SECURITY.md`](SECURITY.md).

> Moved from Supabase Postgres on 2026-10-24 (see `DECISIONS.md` D11). The old SQL migrations are in git history (`supabase/migrations/`, removed); the new backend started with an empty database.

## Schema changes

- Edit `convex/schema.ts`; `npx convex dev` validates and pushes it (existing documents must match, or the push fails). For a change that needs a data backfill on a live deployment, use a migration (`@convex-dev/migrations`) — don't hand-edit production.
- Keep `lib/types/database.ts` (UI wire shapes), `convex/lib/dto.ts` (doc → DTO), and `convex/lib/returns.ts` (return validators) in step.
- **Auth tables**: don't edit `convex/betterAuth/generatedSchema.ts`. Change the Better Auth config in `convex/auth.ts`, then regenerate: `cd convex/betterAuth && npx auth@1.6.33 generate --output generatedSchema.ts -y`.

## App tables (`convex/schema.ts`)

Every document has `_id` and `_creationTime` (used as the timestamp everywhere). Every index implicitly ends in `_creationTime`, so `by_x` indexes are also chronological orderings.

| Table | Fields | Indexes |
|-------|--------|---------|
| `profiles` | `authUserId` (Better Auth user id), `username`, `usernameLower`, `bio?`, `avatarId?` (storage), `accessLevel` (`reserved`\|`full`), `followerCount`, `followingCount`, `postCount`, `suspendedAt?` + `suspendedReason?` + `suspendedUntil?` (admin suspension; no `suspendedUntil` = until restored) | `by_authUserId`, `by_usernameLower` (uniqueness + prefix search), `by_avatar`, `by_accessLevel`, `by_suspendedAt`, `by_suspendedUntil` (expiry cron); search `search_username` |
| `communities` | `name`, `slug`, `description?`, `creatorId`, `privacyType` (`public`\|`invite_only`), `memberCount` | `by_slug`, `by_creator`; search `search_name` |
| `communityMembers` | `communityId`, `userId`, `role` (`member`\|`moderator`\|`creator`) | `by_community`, `by_user`, `by_community_user` |
| `communityInvites` | `communityId`, `inviterId`, `inviteeId?` (targeted) / `token?` (link), `status`, `expiresAt?` | `by_token`, `by_invitee`, `by_inviter`, `by_community`, `by_community_invitee` |
| `posts` | `authorId`, `content`, `imageId?` (storage), `communityId?` (unset = personal), `likeCount`, `commentCount` | `by_author`, `by_author_community` (following feed: `communityId = undefined`), `by_community`, `by_image` |
| `comments` | `postId`, `authorId`, `content`, `parentId?` (thread root) | `by_post_parent` (roots: `parentId = undefined`), `by_parent`, `by_author` |
| `likes` | `postId`, `userId` | `by_post_user`, `by_user` |
| `follows` | `followerId`, `followingId` | `by_follower_following`, `by_follower`, `by_following` |
| `notifications` | `userId` (recipient), `actorId?`, `type`, `postId?`, `commentId?`, `communityId?`, `inviteId?`, `read` | `by_user`, `by_user_read`, `by_actor`, `by_post`, `by_comment`, `by_community` |
| `reservations` | `profileId`, `reasons[]`, `dailySocialMinutes?`, `referralCode`, `referredBy?` | `by_profile`, `by_referralCode`, `by_referredBy` |
| `adminUsers` | `profileId`, `role?` (`owner`\|`moderator`; unset = owner) | `by_profile` |
| `adminActions` | audit log: `actorId?` (unset = CLI / system), `action` (see `adminAction` in `schema.ts`), `targetId?`, `targetUsername?` (snapshot), `reason?`, `details?` | `by_actor`, `by_target`, `by_target_action`, `by_action` |
| `adminNotes` | `targetId`, `authorId?`, `body` (admin-only notes about an account) | `by_target`, `by_author` |
| `appeals` | `profileId`, `body`, `status` (`open`\|`accepted`\|`rejected`), `response?`, `resolvedAt?` | `by_profile`, `by_status` |
| `blockedHandles` | `handleLower`, `match` (`exact`\|`contains`), `note?` | `by_handle` |
| `announcements` | `kind` (`launch`, unique), `subject`, `body`, `status` (`sending`\|`sent`), `recipients` | `by_kind` |
| `appConfig` | `key: "singleton"`, `signupMode` (`reservation`\|`open`) | `by_key` |

**Denormalized counters** (`likeCount`, `commentCount`, `memberCount`, `postCount`, `followerCount`, `followingCount`) are maintained by the mutations and the cascade helpers (`convex/lib/cascade.ts`) — Convex has no `count(*)`. Any new write path that adds/removes a like, comment, member, post, or follow must adjust them (use `bump`).

**No email column anywhere in app tables** — email lives only in the Better Auth `user` table. `admin:reservationList` is the only function that joins it in.

## Auth tables (`betterAuth` component)

Generated by Better Auth for our config: `user` (+ our `signupMeta` field), `session`, `account`, `verification`, `passkey`, `jwks`, `rateLimit`, plus tables for plugins we don't use. App code reads them only through `authComponent` helpers (`safeGetAuthUser`, `getAnyUserById`).

## Triggers & lifecycle (`convex/auth.ts`, `convex/lib/accounts.ts`)

- **`user.onCreate` → `createProfileForAuthUser`** (same transaction as the user insert): creates the profile (username from `signupMeta`, else derived from email/name, de-duplicated on collision), sets `accessLevel` from `appConfig.signupMode`, and in reservation mode inserts the reservation (survey + unique referral code + validated `referredBy`). Replaces the `handle_new_user` SQL trigger.
- **`user.onDelete` → `deleteAllDataForAuthUser`**: deletes the user's communities (cascade), posts (cascade: comments, likes, notifications, image), comments elsewhere (with replies), likes, follows, memberships, invites, notifications, reservation (clearing others' `referredBy`), admin row, the profile links on `adminActions` (rows kept, `actorId`/`targetId` unset), admin notes about them (deleted; notes they wrote are kept with `authorId` unset), their appeals, avatar file, and the profile — fixing counters on other people's content.

## Cascades (`convex/lib/cascade.ts`)

`deletePostCascade`, `deleteCommentCascade`, `deleteCommunityCascade`, `removeMembership` — the equivalents of the old `ON DELETE CASCADE`s, plus counter maintenance.

## Feeds & pagination

- Lists use Convex cursor pagination (`paginationOptsValidator` + `.paginate()`), consumed live by `usePaginatedList` (wraps convex-helpers' `usePaginatedQuery`).
- **Following feed / communities feed**: there's no `IN (...)`, so `convex/feed.ts` opens one index stream per followed author / joined community and merges them by `_creationTime` (`mergedStream` from `convex-helpers/server/stream`). Each stream is an equality lookup on its index prefix, so the merge is exact and strictly reverse-chronological. The following feed reads at most 2000 follows.
- **Profile posts** use a stream with `filterWith(canViewPost)` so hidden community posts are skipped without breaking page sizes.
- **Comments** paginate by root comment (oldest first); each page carries its roots' replies.

## Server config

- `appConfig.signupMode` — set with `npx convex run admin:setSignupMode '{"mode":"open"}'`. Missing row ⇒ `reservation`.
- Admins — `npx convex run admin:grant '{"username":"you"}'`.
